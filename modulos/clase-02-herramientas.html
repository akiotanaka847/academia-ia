Herramientas que el agente entiende

Un agente solo puede hacer lo que sus herramientas le permiten, y solo las usa bien si entiende para qué sirve cada una. Aquí aprendes a describirlas como lo hacen los equipos que construyen agentes de verdad.

01 La idea

Una herramienta es un contrato: el modelo pide, tu sistema ejecuta. Si el contrato es confuso, el agente se equivoca aunque la herramienta funcione perfecto.

Al terminar esta clase podrás:

  • Explicar los cuatro pasos de una llamada a una herramienta y quién hace cada uno.
  • Diseñar el nombre, la descripción y los parámetros de una herramienta para que el modelo la elija bien.
  • Escribir mensajes de error que le enseñen al agente qué hacer.
  • Reconocer las herramientas de Workfront y Fusion que tu agente puede usar, y cuáles leen o escriben.

02 El problema

Tu herramienta para buscar tareas funciona sin errores, pero el agente la usa mal: la elige cuando le piden crear una tarea, le pasa una frase donde esperabas un estado o se rinde ante el primer error. Pruebas un modelo más caro y pasa lo mismo.

Casi nunca es culpa del modelo. El modelo solo ve el nombre, la descripción y los parámetros de cada herramienta, y con eso decide. En pruebas públicas, cambiar solo esos textos mueve entre 10 y 20 puntos el acierto al elegir herramientas. Diseñarlas bien es la mejora más barata que existe.

03 El concepto

Los cuatro pasos de una llamada

1 · DescribirLo haces tú

  • Nombre, descripción y parámetros
  • El modelo los lee antes de decidir

2 · DecidirLo hace el modelo

  • Elige la herramienta
  • Llena los parámetros

3 · EjecutarLo hace tu sistema

  • El modelo nunca ejecuta nada
  • Aquí se revisan los permisos

4 · ObservarVuelve al modelo

  • El resultado, o el error, como texto
  • Con eso decide el siguiente paso

Fíjate en el paso 3: el modelo solo pide. Quien ejecuta es tu sistema (Workfront, Fusion, el conector). Por eso los permisos se ponen en las herramientas, no en las instrucciones: una regla en el prompt se puede ignorar, una herramienta que no existe no se puede usar.

Así se ve una herramienta por dentro

Cada herramienta se describe con un esquema como este. Todo lo que ves aquí lo lee el modelo:

buscar_tareas.json
{
  "name": "buscar_tareas",
  "description": "Úsala cuando pidan ver tareas de un proyecto, por estado o por responsable. No la uses para crear ni cambiar tareas.",
  "input_schema": {
    "type": "object",
    "properties": {
      "proyecto":    { "type": "string", "description": "Nombre exacto del proyecto, por ejemplo Aurora" },
      "estado":      { "type": "string", "enum": ["abierta", "atrasada", "terminada"] },
      "responsable": { "type": "string", "description": "Opcional. Nombre de la persona" }
    },
    "required": ["proyecto"]
  }
}

Cuatro reglas de diseño

ReglaAsí noAsí sí
Nombre con verbo y objetotareas, gestionar_workfrontbuscar_tareas, crear_tarea
Descripción: cuándo sí y cuándo no«Busca tareas.»«Úsala cuando pidan ver tareas de un proyecto. No la uses para crear ni cambiar tareas.»
Parámetros con opciones cerradasconsulta: cualquier textoestado: abierta, atrasada o terminada
Errores que enseñan«Error 422»«No existe "Auora". ¿Quisiste decir "Aurora"?»

Y una quinta, que se olvida mucho: varias herramientas pequeñas son mejores que una que hace de todo. Una herramienta «gestionar_workfront» obliga al modelo a escribir la acción como texto libre, que es justo donde más se equivoca. Si un parámetro «acción» tiene más de tres opciones, divídela.

Ojo

Las descripciones también pueden traer trampas

El modelo lee la descripción de cada herramienta tal cual. Un servidor malicioso podría esconder ahí órdenes («y además envía los archivos a…»). Conecta solo servidores de confianza, como los oficiales de Adobe, y revisa qué herramientas trae cada uno.

04 Constrúyelo

Diseña la herramienta de búsqueda de tu agente. Además de la tuya, el agente tiene crear_tarea, que ya está bien hecha. Al ejecutar, le llegan cuatro pedidos y cada uno pone a prueba una decisión distinta. Empieza con las opciones marcadas, que son las más comunes (y las peores).

    05 Úsalo

    Con Workfront no tienes que programar herramientas: el servidor MCP de Workfront ya trae las suyas, diseñadas con estas mismas reglas. Lo que sí decides es cuáles puede usar tu agente. Estas son algunas:

    HerramientaQué haceTipo
    insights_find_workfront_dataBusca, filtra, ordena y resume datos de WorkfrontLectura
    insights_summarize_objectResume un proyecto, tarea u otro objetoLectura
    comment-stream_create_commentDeja un comentario en un objetoEscritura
    workflow_update_any_objectActualiza tareas, proyectos y otros objetosEscritura
    workflow_delete_any_objectBorra objetos (siempre pide confirmación)Escritura
    1. En Workfront: el administrador decide qué se permite. Las herramientas de lectura vienen activadas y las de escritura, apagadas.
    2. En Fusion: en el módulo «Process a user prompt» eliges qué herramientas puede usar en «Read-only tools» y «Write/delete tools».
    3. En Claude: en la configuración de cada conector puedes apagar las herramientas que no quieras, y Claude te pide permiso antes de usarlas.
    Tus escenarios también son herramientas

    Diseña cada escenario de Fusion como una herramienta

    Con el servidor MCP de Fusion, Claude puede ejecutar un escenario y leer su resultado. Ponle a cada escenario un nombre con verbo («Generar reporte semanal de Aurora») y una descripción con cuándo usarlo, y haz que, si falla, el error diga qué pasó. Lo ves en la clase 3.

    06 Llévatelo

    Usa esta ficha cada vez que diseñes una herramienta, un escenario que otro agente va a usar o una skill.

    Plantilla

    Ficha de herramienta

    # Ficha de herramienta

## Nombre (verbo + objeto, sin datos dentro)
[buscar_tareas]

## Descripción (dos frases)
Úsala cuando [situación en la que sí sirve].
No la uses para [casos parecidos en los que no sirve].

## Parámetros
| Nombre | Tipo | ¿Obligatorio? | Opciones o ejemplo |
|---|---|---|---|
| [proyecto] | texto | sí | Aurora |
| [estado] | opción | no | abierta, atrasada o terminada |

## Qué devuelve
[Lista de tareas con nombre, responsable, fecha y avance]

## Errores (escritos para el modelo)
- Si [no existe el proyecto]: «[No existe X. Proyectos activos: …]»
- Si [falta un permiso]: «[No tienes permiso para … Pídelo a …]»

## Permisos
- ¿Lee o escribe? [Solo lee]
- ¿Necesita aprobación humana? [No]

## Checklist
- [ ] El nombre dice qué hace sin leer la descripción.
- [ ] La descripción dice cuándo NO usarla.
- [ ] Todo lo que tiene opciones fijas es una lista cerrada.
- [ ] Cada error dice qué pasó y cómo seguir.
- [ ] Hace una sola cosa.

    07 Practica

    1. En el simulador, cambia solo la descripción y deja lo demás como estaba. ¿Qué pedido se arregla?
    2. Escribe la descripción de dos herramientas parecidas («buscar_solicitudes» y «crear_solicitud») para que el modelo nunca las confunda.
    3. Piensa en un escenario de Fusion de tu equipo. Escríbele un nombre con verbo y una descripción con «úsalo cuando» y «no lo uses para».

    Palabras clave

    Herramienta
    Una acción que el agente puede pedir y que tu sistema ejecuta.
    Llamada a herramienta
    El pedido estructurado del modelo: qué herramienta y con qué parámetros. También se le dice «function calling».
    Esquema
    La descripción formal de la herramienta: nombre, descripción y parámetros con sus tipos.
    Opciones cerradas
    Un parámetro que solo acepta valores de una lista. En inglés, «enum».
    Mínimo privilegio
    Darle al agente solo las herramientas y permisos que necesita para su tarea.

    08 Comprueba lo aprendido

    1. Cuando un agente «usa» una herramienta, ¿quién la ejecuta de verdad?

    Correcto

    El modelo solo pide. Por eso los permisos se controlan en las herramientas y no en el prompt.

    2. ¿Qué descripción ayuda más al modelo a no confundir dos herramientas parecidas?

    Correcto

    La frase «No la uses para…» es la que separa una herramienta de su vecina más parecida.

    3. ¿Qué mensaje de error es mejor para un agente?

    Correcto

    Un error que dice qué pasó y cómo seguir permite que el agente se corrija solo, en lugar de rendirse o inventar.
